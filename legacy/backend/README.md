# Nibrexo Flask API

Nibrexo keeps its existing Flask routes and static frontend behavior while supporting two database environments:

- local development/tests: SQLite through `NIBREXO_DB_PATH`
- production: Supabase PostgreSQL through `NIBREXO_DATABASE_URL`

Production architecture:

```text
Browser → Vercel → Flask Vercel Function → Supabase PostgreSQL
```

There is no separate Gunicorn, PythonAnywhere, VPS, Redis, or secondary-database deployment.

## Application boundaries

- `backend/app.py:create_app` is the application factory.
- `api/index.py` is the production Vercel entry point.
- `/api/*` remains authoritative for authentication, roles, ownership, CMS, settings, checkout state, and protected customer data.
- Browser adapters continue to use same-origin requests with cookies.
- Vercel serves allowlisted frontend output generated by `scripts/build_vercel_static.py`.
- `NIBREXO_API_ONLY=true` prevents the serverless function from serving repository files.

## Dependencies

`backend/requirements.txt` is authoritative. Root `requirements.txt` delegates to it because Vercel installs Python dependencies from the project root.

```bash
python -m pip install -r requirements.txt
```

Runtime dependencies include Flask, Cryptography, and Psycopg 3 with its binary package. Gunicorn is not a production dependency.

## Database and migrations

```bash
python backend/manage.py migrate
python backend/manage.py migration-status
```

Logical migration order:

1. `001_initial`
2. `002_forward_schema`
3. `003_site_settings`
4. `004_login_rate_limits`

SQLite selects `001_initial.sql`; PostgreSQL selects `001_initial.pg.sql`. Migration versions are recorded once under the logical name in `schema_migrations`. Normal application startup checks status but never applies migrations.

PostgreSQL connections are short-lived, use mapping rows, disable automatic prepared statements for transaction-pooler compatibility, and close after each explicit operation. Runtime SQL compatibility is limited to the audited application surface; migration SQL is engine-specific where required.

## Authentication

Authentication continues to use opaque database-backed sessions:

- a random token is sent only in the `nibrexo_session` cookie,
- only its SHA-256 hash is stored in `sessions`,
- `/api/auth/me` validates the database session, expiry, revocation, and active user,
- logout revokes the token,
- password reset revokes all active sessions.

Production cookies are `Secure`, `HttpOnly`, `SameSite=Lax`, host-only, and scoped to `/`. The embedded development-preview cookie behavior is not considered evidence of real Vercel behavior.

## Login throttling

`login_attempts` stores only a SHA-256 key derived from normalized email plus canonical client IP, a failure count, and window timestamps.

- maximum failures: 5
- window: 15 minutes
- sixth attempt: HTTP `429`
- successful login: clears the key
- production storage: PostgreSQL
- no production in-memory fallback

## First Owner

Public registration always creates a customer. `/setup/owner` is development-only and is disabled in production and API-only mode.

Local interactive setup:

```bash
python backend/setup_admin.py --interactive --role owner
```

Later production provisioning must run from an operator-controlled process after migrations, with `NIBREXO_DATABASE_URL` and the existing one-time `NIBREXO_FOUNDER_EMAIL`, `NIBREXO_FOUNDER_NAME`, and `NIBREXO_FOUNDER_PASSWORD` values injected securely. The command does not print or persist the raw password.

## Production configuration

Required:

- `NIBREXO_ENV=production`
- `NIBREXO_DATABASE_URL`
- `FLASK_SECRET_KEY` (non-default, at least 32 characters)
- `LICENSE_ENCRYPTION_KEY` (valid Fernet key)
- `NIBREXO_COOKIE_SECURE=true`

Optional existing settings include license key version/history, session/reset durations, and provider configuration. `NIBREXO_DB_PATH` is local-only.

## Workflow worker

`backend/worker.py` and `backend/workflows.py` business logic is unchanged. It is not deployed in Phase 1. Workflow definitions and queued rows remain supported, but queued executions will remain pending until a separately approved Vercel-compatible execution design exists. Current provider adapters are not connected.

## Backup boundary

`backend/backup.py` supports local SQLite only and refuses PostgreSQL mode. Supabase backup, retention, and restore operations must use approved PostgreSQL/Supabase procedures.

## Verification status

Local tests verify SQLite behavior, SQL translation, migration selection, login throttling, Vercel entry-point structure, and fail-closed configuration. No live Supabase migration or Vercel browser authentication has been performed.
